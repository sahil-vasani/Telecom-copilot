Telecom Copilot Project – Data Collection & Overall Data Flow


Step 1: Why did we need our own dataset?
The goal of this project was to build a Telecom Customer Support AI Assistant using Retrieval-Augmented Generation (RAG).

Large Language Models already know general knowledge, but they do not reliably know company-specific telecom policies, recharge procedures, APN settings, or telecom regulations. Even when they know something, the information may be outdated or hallucinated.

Step 2: Which datasets could have been used?
Option 1 — Collect everything manually
One possibility was to manually create thousands of telecom question-answer pairs.
Disadvantages

Extremely time-consuming
Requires telecom experts
Difficult to scale
Expensive

Option 2 — Scrape telecom websites
Disadvantages

Different website structures
Frequent website updates
Legal and copyright considerations
Large amount of cleaning required

Option 3 — Use an existing public telecom dataset
there is no large, high-quality, open-source telecom customer support dataset comparable to datasets like MultiDoc2Dial.

Most public customer-support datasets belong to banking, government services, or general help desks.

Therefore, relying only on public telecom datasets was not possible.

Step 3: Why was MultiDoc2Dial selected?
Instead of searching only for telecom datasets, I searched for datasets that teach customer support conversations.
The best publicly available dataset was MultiDoc2Dial.
It contains:

real customer conversations
agent responses
document grounding
document references

Why didn't I use MultiDoc2Dial alone?

Because its documents belong to domains like:

government
public services
insurance
benefits

It contains almost no telecom-specific information.

If I trained only on MultiDoc2Dial, the chatbot would not know:

APN settings
recharge plans
SIM activation
telecom billing
network troubleshooting
roaming
TRAI regulations

Therefore, an additional telecom knowledge base was required.

Step 4: Building a Telecom Knowledge Base
To overcome the lack of telecom data, I created my own telecom corpus.
Instead of depending on one source, I combined information from multiple trusted sources
The knowledge base includes information derived from:

BSNL Customer Charter

General telecom troubleshooting
Manually written synthetic passages

The telecom dataset is mostly synthetic, but it is not randomly generated.
The process was:

Read official telecom documents.
Read carrier FAQs.
Understand common telecom problems.
Rewrite and standardize the information into a common format.
Write additional missing FAQs manually.
Store every passage with metadata.

Step 5: Why was SHP-2 used?
Its purpose is not retrieval.

Its purpose is not knowledge storage.

Instead, SHP-2 teaches the model:

Which answer is better when two responses are available.

MultiDoc2Dial	Teaches grounded customer support conversations and document retrieval
Telecom Knowledge Base	Provides telecom-specific domain knowledge missing from public datasets
SHP-2	Teaches the model to prefer better, clearer responses during preference optimization

kb_builder.py — Building the Knowledge Base (KB)

Purpose of this file

After collecting data from different sources, the data is still scattered and stored in different formats.

For example:

MultiDoc2Dial stores documents in its own Hugging Face dataset format.
My telecom dataset is stored as passages.jsonl.
Telecom overlay articles are written directly inside Python.

Therefore, the purpose of kb_builder.py is to convert every source into one unified knowledge base with a common schema so that every passage looks identical regardless of where it came from

Without this step:

every dataset would have a different format,
searching would become inconsistent,
retrieval quality would decrease.

Although MultiDoc2Dial already contains documents, those documents belong to only four domains

DMV: Department of Motor Vehicles
SSA: Social Security Administration
FSA (or FSA-Student Aid): Federal Student Aid
VA: Veterans Affairs

The file builds the KB in two layers.
Layer 1 — MultiDoc2Dial Documents
The first layer loads the original MultiDoc2Dial documents.

These are real customer-support documents that are already linked to the conversation dataset.

Layer 2 — Telecom Knowledge

The second layer adds telecom-specific information.

It includes:

Telecom overlay documents
Generated telecom corpus (passages.jsonl)


Why not train only on telecom data?

There are two reasons.

Reason 1

The telecom corpus is relatively small.

Training an entire RAG model using only this data would likely reduce generalization.

Reason 2

MultiDoc2Dial already provides professionally annotated customer-support conversations with document grounding.

Combining both datasets gives:

realistic customer-support conversations
telecom domain knowledge

Complete Project Flow (Till training_data_builder.py)

The first step of my project is download_datasets.py. Since a Retrieval-Augmented Generation (RAG) chatbot needs data before it can answer any questions, this script downloads all the required datasets from Hugging Face and stores them locally. It downloads the MultiDoc2Dial dialogue dataset, which contains customer and support-agent conversations, the MultiDoc2Dial document dataset, which contains the documents used by agents to answer customer questions, and the SHP-2 (Stanford Human Preferences) dataset, which contains prompts along with two different responses where one response has been preferred by humans over the other. The SHP-2 dataset is not used for answering questions; instead, it is used later for DPO (Direct Preference Optimization). DPO is the final fine-tuning stage where the language model learns which response is better when multiple responses are possible, making the chatbot's answers more natural, helpful, and aligned with human preferences. After downloading, all datasets are stored in the data/raw folder so they can be reused without downloading again.

The next step is kb_builder.py. The main purpose of this file is to build the Knowledge Base (KB). A Knowledge Base is simply a collection of all the information that the chatbot can search when answering a user's question. Instead of searching the internet or raw datasets every time, the chatbot searches this organized knowledge base. First, kb_builder.py loads the MultiDoc2Dial document dataset and converts every document into small searchable passages with information such as passage ID, document ID, title, text, category, and source. Then it loads the telecom knowledge that was created using the telecom corpus builders, including information about billing, recharge, SIM activation, APN settings, roaming, network issues, customer support, device setup, and TRAI guidelines. Since these datasets come from different sources and have different formats, kb_builder.py converts all of them into one common format and merges them into a single knowledge base. Finally, it creates kb_passages.jsonl, which contains all searchable passages, doc_index.json for document lookup, span_index.json for mapping passages to their original documents, and dataset_stats.json for statistics. The final knowledge base contains 26,104 passages, including 24,933 MultiDoc2Dial passages and 1,171 telecom passages, across 498 documents, containing approximately 407,938 words. This knowledge base is later searched by the retriever whenever a user asks a question.

After the knowledge base is created, the next step is training_data_builder.py. Although the knowledge base contains all the information, machine learning models cannot be trained directly from it. Different models require different types of training data. Therefore, this file converts the knowledge base and dialogue data into several specialized datasets. First, it loads the MultiDoc2Dial dialogues and the span index created during the previous step. Using this information, it creates the Retriever Training Dataset. The retriever is the part of the RAG system that finds the most relevant passage from the knowledge base for a user's question. To train it, the script creates examples consisting of a user query, the correct passage (positive example), and similar but incorrect passages (hard negatives). This teaches the retriever how to distinguish the correct passage from other similar passages. The script also creates additional telecom-specific retriever examples by generating realistic telecom queries from telecom passages and pairing them with appropriate positive and negative passages. Finally, both datasets are merged into retriever_train.jsonl, which is later used to train the retriever model.

Next, the script creates the Generator Training Dataset. The generator is the language model that writes the final answer after the retriever has found the relevant information. To train the generator, the script combines three things: the user's question, the retrieved context from the knowledge base, and the correct answer given by the support agent. These examples are saved as generator_sft_train.jsonl and are used for Supervised Fine-Tuning (SFT), where the model learns how to generate accurate, grounded responses based on the retrieved context.

After creating the generator dataset, the script prepares the DPO Training Dataset. DPO stands for Direct Preference Optimization. While Supervised Fine-Tuning teaches the model how to answer, DPO teaches the model which answer is better when multiple answers are possible. For this purpose, the script creates preference pairs consisting of a prompt, a preferred (chosen) response, and a less preferred (rejected) response. These preference pairs are created from both MultiDoc2Dial and the SHP-2 dataset. During DPO training, the model learns to generate responses that are closer to the preferred human responses and avoid responses that humans consider less useful. The final preference dataset is stored in dpo_pairs.jsonl.

Finally, training_data_builder.py creates the Evaluation Dataset. This dataset is not used for training. Instead, it is used after training to measure how well the complete RAG system performs. The evaluation dataset contains customer questions, the correct document, the correct answer, and several handcrafted telecom scenarios such as roaming issues, billing disputes, network outages, complaint escalation, and eSIM activation. These examples are saved in test_cases.jsonl and are later used to evaluate retrieval accuracy, response quality, and overall chatbot performance.

At the end of this stage, the project has successfully prepared all the datasets required for training and evaluation. Specifically, it generates:

retriever_train.jsonl → used to train the Retriever, which finds the correct passage from the Knowledge Base.
generator_sft_train.jsonl → used to train the Generator, which produces the final answer.
dpo_pairs.jsonl → used for Direct Preference Optimization (DPO) so the model learns to prefer better human-like responses.
test_cases.jsonl → used to evaluate the complete RAG system after training.

why use flan-t5 ?
We needed a model that could generate answers from retrieved documents
FLAN-T5-Small is an instruction-tuned Seq2Seq model so it already understands question-answering tasks
It is lightweight, fast to fine-tune, and can run on limited GPU resources while still providing good generation quality
FLAN-T5-Small offered the best balance between performance and computational cost

Why not BERT?
BERT is an encoder-only model. It is mainly designed for understanding text, such as classification or sentiment analysis. Our task requires generating complete answers, so BERT is not suitable for answer generation.

Why not GPT
GPT models are decoder-only models and are excellent at text generation. However, FLAN-T5 is an instruction-tuned Seq2Seq model, which naturally fits tasks where we provide context and ask a question. It is also much lighter and easier to fine-tune on limited hardware

Why not Mistral?
Mistral is a much larger decoder-only language model that generally produces better responses

Why not Llama?
Llama models provide excellent generation quality but are considerably larger and require more GPU memory and longer training time

Why not T5 (Original)?
FLAN-T5 is built on T5 but is instruction-tuned. Because of this additional instruction tuning, it follows prompts and question-answering instructions much better than the original T5

Why not train from scratch?
Training a language model from scratch requires enormous datasets, weeks of training, and expensive GPU clusters
